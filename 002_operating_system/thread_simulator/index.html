Lab 1

Process vs Thread

A new process gets its own separate memory. A new thread lives inside an existing process and shares that process's code, data and heap, and only gets its own stack, registers and program counter. Select a process, then add a thread or create a child process and watch what is shared and what is private.

Concepts

Why threads?

A process is a program in execution with its own address space. A thread is the smallest unit of CPU execution inside a process. A process always has at least one thread, and it can create more.

Every thread has its own program counter, registers and stack, so each one can be at a different point in the code. All threads of a process share the code, the global data, the heap and the open files.

  • Responsiveness: one thread can keep the interface alive while another waits for a disk or the network.
  • Resource sharing: threads reach the same data directly, with no message passing between processes.
  • Economy: creating a thread and switching between threads costs less than doing the same with processes, because no new address space is needed.
  • Scalability: a multithreaded program can spread its work over several cores.
Worth knowing: sharing memory is both the strength and the risk of threads. There is no protection between threads of one process, so a bug or crash in one thread can corrupt data or bring down every thread in that process.

Remember: a process is heavier to create and needs IPC to talk to other processes. A thread is lighter to create and talks to its siblings directly through shared memory, which needs care. Because the memory is shared, a crashing thread can bring down the whole process.

Concepts

Concurrency vs parallelism

Concurrency means several tasks are in progress during the same period. Parallelism means several tasks are executing at the exact same instant. You can have concurrency without parallelism, but parallelism needs more than one core.

On a single core the scheduler gives each thread a short turn on the CPU and switches fast enough that they all seem to move together. With several cores, different threads really do run side by side. The OS scheduler decides which ready thread gets which core.

When a thread starts waiting for I/O it leaves the CPU, and the scheduler hands that core to another ready thread. This is why threads help even on one core: the CPU stays busy while a thread waits.

Worth knowing: more cores do not always mean proportionally faster. Work that must run in order cannot be split, so the longest chain of steps sets the minimum time. That limit is described by Amdahl's law: the serial part of a program caps the speed-up you can get from extra cores.

Remember: on one core the threads only take turns (concurrent). With several cores they can truly run at the same instant (parallel). A thread waiting for I/O does not need the CPU, so another thread uses the core meanwhile. The main thread needs 7 ticks by itself (2 + 3 + 2), so more cores cannot finish sooner than that.

Not guaranteed: this lab assumes the OS spreads the threads over free cores. In real life you cannot count on it. The OS scheduler decides which core runs which thread, and it could put two threads on the same core.
